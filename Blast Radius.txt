	Este protocolo es de cumplimiento obligatorio para el agente LLM y lo conoceremos en adelante con el nombre Blast Radius
Tu objetivo es garantizar que cada cambio sea predecible, no rompa funcionalidades existentes y sea compatible con todos los navegadores modernos:
1. Análisis de Impacto y Dependencias: Antes de proponer cambios, el agente debe realizar una fase de "Exploración Profunda" usando herramientas de búsqueda (grep, find, ls): Búsqueda de Referencias: No solo inspeccionar el archivo a modificar, sino buscar en todo el proyecto quién consume esa función, componente o API.Identificación de Contratos: Verificar si el cambio altera interfaces (TypeScript), esquemas de base de datos o contratos de API que otros módulos esperan.Revisión de Estilos Globales: Si se modifica CSS/Tailwind, verificar si las clases son compartidas para evitar efectos visuales no deseados en otras páginas. Análisis de Compatibilidad (Can I Use): Verificar si las propiedades de CSS o APIs de JS propuestas son compatibles con:Chromium: Chrome y Edge.Gecko: Firefox.WebKit: Safari (macOS/iOS).
2. Plan de Implementación Detallado El agente presentará un plan estructurado. No se permite escribir código sin la aprobación de este plan. ✅ Arquitectura del Cambio, Archivos a Modificar: Rutas exactas. Archivos Afectados (Indirectos): Lista de archivos que podrían verse impactados por el cambio (regresiones potenciales). ✅ Estrategia de Diseño Web y CompatibilidadCross-Browser: Especificar si se usarán polyfills o prefijos para asegurar el funcionamiento en Safari (iOS/macOS), Firefox y Edge.Responsividad: Cómo se adaptará el cambio a diferentes viewports (móvil, tablet, desktop).Accesibilidad (A11y): Asegurar que los cambios no rompan la navegación por teclado o lectores de pantalla.✅ Manejo de Casos Borde y Errores de Comportamiento ante: Carga lenta, falta de datos, errores de red y desbordamiento de contenido (UI).
3. Estrategia de Pruebas y ValidaciónEste apartado es crítico para evitar el "impacto colateral" mencionado en el curso. NivelAcción EspecíficaRegresión Ejecutar la suite de pruebas existente (npm test o similar) para asegurar que lo antiguo sigue funcionando. Unitarias Crear tests para la nueva lógica (ej. Vitest/Jest). Visual/CSSVerificar el renderizado en contenedores que simulen diferentes motores (Chrome vs Safari).Cross-Browser(Si hay herramientas E2E como Playwright) Ejecutar tests en los proyectos de chromium, firefox y webkit. ManualLista de pasos para que el usuario verifique el cambio en su navegador Apple/Safari.
4. Pausa de Seguridad y Aprobación El agente se detendrá y presentará el resumen:¿Qué se va a hacer?¿Qué podría romperse? (Riesgos identificados).¿Cómo hemos asegurado que funcione en Safari/Chrome/Firefox? Pregunta obligatoria: "He analizado el impacto en el sistema y la compatibilidad entre navegadores. ¿Deseas que proceda con la implementación según este plan? (sí/no)"
5. Implementación Controlada Una vez recibida la aprobación: Cambios Atómicos: Realizar modificaciones pequeñas y lógicas. Linting & Formatting: Ejecutar herramientas de estilo (Eslint/Prettier) para mantener la consistencia. Comentarios de Código: Explicar por qué se tomó una decisión técnica específica si afecta a la compatibilidad (ej. "Fix para Safari: flex-basis bug").
6. Verificación Post-Cambio (Diff y Auditoría) Al terminar, el agente debe informar: Resumen de Cambios (Diff): (+) Añadido, (~) Modificado, (-) Eliminado. Resultado de Tests: Confirmación de que las pruebas de regresión pasaron exitosamente. Notas de Compatibilidad: Confirmar que no se usaron APIs "deprecadas" o no soportadas por Safari o Firefox.   
7. Definiciones: Si El agente tuviera que realizar inferencias o suposiciones como parte de las aprobaciones necesarias presentara preguntas con opciones para que yo pueda elegir y re alimentar para solucionar cualquier duda.
8 Checkpoints: Una vez aprobado el plan, El agente Genera puntos de control por si se vence la longitud de contexto o se agota el tiempo para poder continuar con el plan.
9. Readme.md: Si algún ajuste obliga al ajuste del readme del directorio raíz del proyecto realiza la corrección y documenta muy brevemente -no mas de un parrafo- el objetivo del cambio.
