1. Frontend Architecture

Strategic Delivery

Advanced Rendering with Next.js

Choose the right rendering strategy based on freshness, personalization, SEO, latency, and infrastructure cost.

Performance + Cost

Decision Strategy

Use SSG for static or rarely changing content: marketing, documentation, blogs, landing pages.
Use ISR for large catalogs, product detail pages, news-like pages, and content that can tolerate a small stale window.
Use RSC as a bundle governance tool alongside ISR: keep heavy logic on the server and reduce client-side JS payloads to improve mobile LCP.
Use SSR only when data must be personalized or fresh per request.
Interview line: “I treat SSR, SSG, and ISR as a spectrum between data freshness and cost efficiency. I prefer ISR for massive catalogs because it maximizes CDN cacheability while controlling cloud egress and compute costs.”
Interview line: “I treat rendering as a spectrum between data freshness and infrastructure cost; ISR is my preference for global scale.”

Decision Parameters

  • Freshness: How quickly must the user see updated data?
  • Personalization: Is the page unique per user/session?
  • SEO: Does search visibility matter?
  • Traffic pattern: predictable, bursty, global, or long-tail?
  • Cost: Are repeated server renders creating unnecessary compute or egress?
  • Latency: Is TTFB affected by server work or origin distance?
  • Bundle Size: Will moving this logic to the server improve mobile LCP?
  • Edge Utility: Can we handle auth or geolocation before hitting the origin?

Contextual Glossary

SSR

Server-Side Rendering. HTML is generated on the server for every request. Strong for personalization and fresh data, but less cacheable and more expensive at scale.

SSG

Static Site Generation. HTML is generated at build time and served as static files. Very fast and cheap, but not ideal for highly dynamic data.

ISR

Incremental Static Regeneration. Static pages can be regenerated in the background after a defined interval. Good balance for large catalogs.

CDN

Content Delivery Network. Globally distributed cache that serves assets closer to users, reducing latency, origin load, and egress cost.

TTFB

Time To First Byte. Measures how long the browser waits before receiving the first byte from the server. Heavy SSR can increase it.

LCP

Largest Contentful Paint. Core Web Vital measuring when the largest visible content appears. Improved through image optimization, caching, and reduced JS.

Cache Invalidation

The process of removing or refreshing stale cached content. Often the hardest part of CDN-heavy architectures.

Revalidation Window

The time interval after which ISR content becomes eligible for regeneration. Shorter windows increase freshness but may increase compute.

React Server Components & Bundle Size Management

Move non-interactive logic to the server to reduce client-side JavaScript and improve mobile experience.

UX + Bundle Control

Decision Strategy

Use RSC for data fetching, heavy libraries, formatting, and non-interactive UI sections.
Use Client Components for browser APIs, stateful interactions, forms, gestures, and real-time UI.
Interview line: “RSC is not only a rendering feature; it is a bundle governance tool. It prevents unnecessary JavaScript from reaching the client.”
Interview line: “I use RSC as a bundle governance tool to keep heavy logic on the server and reduce client-side JS payloads — the result is a noticeably faster mobile experience.”

Decision Parameters

  • Does this component need interactivity?
  • Does it use browser-only APIs?
  • Can the logic stay on the server safely?
  • Will moving it server-side reduce client bundle size?
  • Does it improve LCP, INP, or mobile performance?

Contextual Glossary

RSC

React Server Components. Components rendered on the server that do not ship their logic to the browser unless interactivity is required.

Client Component

A React component that runs in the browser and supports state, effects, event handlers, and browser APIs.

Hydration

The process where React attaches interactivity to server-rendered HTML. Too much hydration can slow the page.

Bundle Size

Total JavaScript downloaded by the browser. Smaller bundles improve startup time and mobile performance.

Code Splitting

Breaking JavaScript into smaller chunks loaded only when needed.

INP

Interaction to Next Paint. Core Web Vital measuring responsiveness after user interactions.

Edge Runtime & Middleware

Make request-level decisions before traffic reaches origin infrastructure.

Latency + Governance

Decision Strategy

Use Edge for lightweight logic: redirects, localization, geolocation, feature flags, A/B tests, auth checks, bot filtering.
Avoid Edge for heavy computation, long-running tasks, large dependencies, or complex database access.
Interview line: “Middleware at the edge is my first line of defense for routing, segmentation, and lightweight policy enforcement.”

Decision Parameters

  • Can this decision be made without hitting the origin?
  • Does it reduce latency or origin load?
  • Is the logic deterministic and lightweight?
  • Does it require secrets, DB connections, or heavy packages?

Contextual Glossary

Edge Runtime

Execution environment close to the user, often used for ultra-low-latency request processing.

Middleware

Code that intercepts requests before they reach routes or APIs. Useful for auth, redirects, and request enrichment.

Origin Server

The primary backend or hosting server that generates or stores the original response.

A/B Testing

Experiment method where users are routed to different variants to measure business or UX impact.

Feature Flag

Runtime switch used to enable, disable, or segment functionality without redeploying.

Rate Limiting

Controlling request volume to protect systems from abuse, overload, or cost spikes.

2. Mobile Ecosystem

Native Performance

JSI & TurboModules Migration

Reduce bridge overhead and enable faster native interoperability.

Native Bridge

Decision Strategy

Use JSI/TurboModules when the app handles heavy native processing, cryptography, real-time data, or performance-sensitive SDKs.
Prioritize JSI specifically when JSON serialization becomes a structural bottleneck for high-frequency data crossing the native boundary.
Delay migration if the app is mostly forms/content and the bridge is not a bottleneck.
Interview line: “I would prioritize JSI when JSON serialization between JS and native becomes a structural bottleneck, not as a cosmetic migration.”
Interview line: “Business logic can be asynchronous, but the user interface must never feel blocked or stuttering.”

Decision Parameters

  • Is the app dropping frames during native calls?
  • Are large payloads crossing the JS-native boundary?
  • Do we need synchronous native access?
  • Are third-party native modules compatible?
  • Does the migration reduce startup time or memory pressure?

Contextual Glossary

JSI

JavaScript Interface. Allows JavaScript to communicate directly with C++ objects, reducing bridge serialization overhead.

TurboModules

New native module system in React Native that supports lazy loading and faster access to native capabilities.

Bridge

Legacy communication layer between JavaScript and native code, often involving asynchronous serialized messages.

JSON Serialization

Conversion of data into JSON strings for transport. Can become expensive for large or frequent payloads.

Native Module

Code written in platform-native languages such as Swift, Objective-C, Kotlin, Java, or C++ and exposed to JS.

Memory Pressure

Condition where the app consumes excessive memory, increasing crash risk or OS-level termination.

Fabric & Reanimated for Perceived Quality

Keep gestures and animations smooth even when business logic is asynchronous or delayed.

UX Fluidity

Decision Strategy

Use Reanimated for gestures, transitions, and animations that must remain smooth under JS load.
Adopt Fabric when the app is ready for the new React Native architecture and needs better rendering coordination.
Interview line: “Business logic can be asynchronous; the interface should never feel blocked.”

Decision Parameters

  • Are gestures or animations stuttering?
  • Is the JS thread overloaded?
  • Does the app need 60fps interactions?
  • Are we building premium mobile experiences where perceived quality matters?

Contextual Glossary

Fabric

New React Native rendering architecture that improves coordination between React and native UI rendering.

Reanimated

Animation library that can run animations on the UI thread, reducing dependency on the JS thread.

UI Thread

Native thread responsible for rendering and user interface responsiveness.

JS Thread

Thread running JavaScript business logic. If overloaded, it can delay UI updates unless animations are moved off it.

60fps

Target of 60 frames per second. A practical threshold for smooth visual interactions.

Perceived Performance

How fast and smooth the app feels to the user, even if backend operations are still pending.

FlashList

A high-performance list alternative to FlatList that uses view recycling to save memory and improve scroll performance.

4. Cloud Infrastructure

Scalability & Governance

Cloud Run vs GKE

Balance agility, control, governance, operational maturity, and workload complexity.

Governance vs Agility

Decision Strategy

Use Cloud Run for stateless APIs, event-driven workloads, bursty traffic, and teams that need fast delivery with low ops overhead.
Use GKE for complex microservice platforms, service mesh, stateful workloads, custom networking, or stronger operational control.
Interview line: “Cloud Run optimizes agility and cost for stateless services; GKE is justified when platform complexity requires Kubernetes-level control.”

Decision Parameters

  • Stateless or stateful?
  • Need service mesh?
  • Need scale-to-zero?
  • Operational maturity of the team?
  • Traffic predictability?
  • Security/networking requirements?

Contextual Glossary

Cloud Run

Managed container platform for stateless services with autoscaling and scale-to-zero behavior.

GKE

Google Kubernetes Engine. Managed Kubernetes for complex container orchestration and platform control.

Scale-to-zero

Serverless behavior where instances drop to zero when idle, reducing cost.

Stateless API

Service that does not store session-specific state locally, making it easier to scale horizontally.

Service Mesh

Infrastructure layer that manages service-to-service communication, retries, mTLS, observability, and traffic policy.

Stateful Set

Kubernetes workload type for applications requiring stable identity and persistent storage.

Decision Strategy

Use IAP to secure internal tools based on user identity and context instead of exposing VPN-only access.
Use VPC Service Controls to reduce data exfiltration risk around sensitive GCP services.
Interview line: “I would move beyond traditional VPNs and apply Zero Trust: identity, device context, and service boundaries must be continuously evaluated.”

Decision Parameters

  • Are consultants or external teams involved?
  • Is access tied to identity and context?
  • Could data be exfiltrated outside approved boundaries?
  • Do we need auditability for regulated environments?

Contextual Glossary

IAP

Identity-Aware Proxy. GCP access control layer that authorizes users based on identity and context before reaching applications.

Zero Trust

Security model that assumes no implicit trust and continuously verifies users, devices, and requests.

VPC Service Controls

GCP security mechanism that creates perimeters around cloud services to reduce data exfiltration risk.

Network tunnel that grants access to private resources. Useful, but weaker than identity-aware controls when used alone.

Principle of granting only the minimum access needed for a user or system to perform its function.

5. Advanced Search & Data

Relevance + Efficiency

Hybrid Search with RRF

Combine keyword precision with semantic understanding to improve search relevance.

Search Quality

Decision Strategy

Use BM25 when exact keywords, titles, SKUs, product names, or legal text matter.
Use dense vectors when user intent is ambiguous, natural language driven, or semantically broad.
Use RRF to combine rankings without overfitting to one search method.
Evaluate search intent: if the query is conceptual use semantic, if it is SKU/title-based use lexical, and when uncertain blend both with RRF.
Interview line: “Hybrid search helps users who do not know the exact keyword. It combines lexical precision with semantic intent.”
Interview line: “Hybrid search bridges the gap between what users type and what they actually intend to find.”

Decision Parameters

  • Do users search exact terms or natural language?
  • Is recall more important than precision?
  • Are synonyms and intent common?
  • Do we need explainability?
  • Can we afford vector index cost?

Contextual Glossary

BM25

Keyword ranking algorithm that scores documents based on term frequency and relevance. Strong for exact lexical matching.

Dense Vectors

Numerical representations of meaning generated by embedding models. Useful for semantic similarity.

Embeddings

Vector representations of text, images, or entities used for semantic search and recommendations.

Semantic Search

Search based on meaning and intent rather than exact keyword overlap.

Hybrid Search

Combination of lexical and semantic search to improve relevance.

RRF

Reciprocal Rank Fusion. Method for combining multiple ranked result lists into a more balanced final ranking.

Valkey & Multi-tenancy

Cache Governance

Decision Strategy

Use consolidated Valkey when tenants can be safely isolated through namespaces, quotas, and access controls.
Use isolated instances when regulatory, noisy-neighbor, or blast-radius risks are unacceptable.
Audit unit economics: are we paying for unnecessary idle cache instances that could be consolidated under namespaces to reduce TCO?
Interview line: “I would avoid Memorystore sprawl by consolidating tenants where isolation can be enforced technically and operationally.”
Interview line: “Consolidate Valkey tenants using namespaces to avoid Memorystore sprawl and reduce TCO — isolation can be enforced technically without requiring separate instances.”

Decision Parameters

  • How sensitive is tenant data?
  • Can namespaces and ACLs enforce isolation?
  • What is the blast radius of failure?
  • Are usage patterns predictable?
  • Are we creating operational sprawl?

Contextual Glossary

Valkey

Open-source Redis-compatible in-memory data store used for cache, sessions, queues, counters, and pub/sub.

Redis

Popular in-memory data store historically used for caching, queues, sessions, and low-latency data access.

Multi-tenancy

Architecture where multiple customers or workloads share infrastructure while remaining logically isolated.

Noisy Neighbor

One tenant consumes excessive resources and degrades performance for others.

Blast Radius

Scope of impact when a component fails or is compromised.

7. Sanity CMS

Headless Content

Sanity Architecture & GROQ Queries

Model content schemas, query with GROQ, and connect Sanity to Next.js via ISR webhooks.

Content Architecture

Decision Strategy

Design schemas top-down: start from content types (article, product, author) and model relationships as references, not embedded objects, to avoid duplication.
Use GROQ projections to fetch only the fields the frontend needs — avoid over-fetching from the Content Lake.
Trigger ISR revalidation via Sanity webhooks on document publish so Next.js pages regenerate without a full redeploy.
Use Preview Mode with draft=true GROQ filter to let editors see unpublished content on the live site securely.
Interview line: "I treat Sanity as the single source of truth for content structure. I model references over embedding, so editors can reuse content without duplication, and GROQ projections keep the API surface lean."

Decision Parameters

  • Are content types reused across pages? Use references, not inline objects.
  • Does the frontend need real-time preview? Configure draft-mode API route.
  • How fast must edits appear? Wire webhooks to Next.js revalidate endpoint.
  • Are images handled efficiently? Use Sanity CDN image pipeline with auto-format and width params.
  • Do multiple teams edit? Use roles and document-level access control.
  • Is content structured or rich text? Use Portable Text for flexible rendering.

Contextual Glossary

GROQ

Graph-Relational Object Queries. Sanity's query language. Supports filtering, projections, joins via references, and ordering. Example: *[_type == "article" && !(_id in path("drafts.**"))] | order(publishedAt desc) { title, slug, author->{name} }

Content Lake

Sanity's hosted document store. Stores all content as JSON documents. Queried via GROQ over HTTPS.

Portable Text

Structured rich-text format stored as JSON arrays of blocks. Rendered on the frontend via @portabletext/react. Supports custom block types (images, embeds, callouts).

Schema

TypeScript/JS definition of document types and their fields. Lives in the Sanity Studio config. Defines field types, validation rules, and UI hints.

References

Links between Sanity documents. Allow content reuse without duplication. Resolved at query time with the arrow operator: author->{name, image}.

Webhook (Sanity)

HTTP POST triggered when documents are created, updated, or published. Used to call Next.js revalidate API and invalidate ISR cache pages.

Sanity Studio, Preview & Deployment

Configure the CMS editing experience, access control, and multi-environment content strategy.

CMS Operations

Decision Strategy

Deploy Studio embedded inside the Next.js app at /studio for a unified deployment pipeline, or standalone if editorial teams need independence.
Use multiple datasets (production, staging) to isolate editorial experiments from live content, but sync schemas carefully.
Configure roles (editor, developer, admin) to limit who can publish or delete documents — especially important for regulated or high-traffic content.
Interview line: "I embed Sanity Studio inside the Next.js monorepo so content schema changes and frontend rendering changes ship together, reducing the risk of a schema migration breaking the live site."

Decision Parameters

  • Does the editorial team need independence from deploys? Use standalone Studio.
  • Are there multiple environments (staging, prod)? Use datasets per environment.
  • How sensitive is content access? Configure RBAC roles.
  • Does the site need live-preview while editing? Use Sanity Presentation tool.
  • Are schema changes frequent? Use migrations CLI to evolve documents safely.

Contextual Glossary

Sanity Studio

React-based CMS editing interface. Configurable via schema definitions. Can be embedded in Next.js or deployed standalone.

Dataset

A scoped content store within a Sanity project. Commonly used to separate production from staging content.

Preview Mode (Next.js + Sanity)

API route that sets a cookie enabling draft document fetching. Allows editors to see unpublished changes on the live Next.js site.

Role-Based Access Control. Controls which users can read, edit, publish, or delete documents in Sanity Studio.

On-the-fly image transformation CDN. Supports width, height, format (webp/avif), fit, and crop params via URL query strings.

8. Elasticsearch

Search + Personalization

Elasticsearch Fundamentals & Index Design

Model indices for search and personalization workloads on a sports/media platform.

Index Architecture

Decision Strategy

Design mappings explicitly: never rely on dynamic mapping in production. Define field types (keyword vs text vs dense_vector) upfront to control how data is indexed and queried.
Use keyword fields for exact matches, filtering, sorting, and facets (categories, IDs, tags). Use text fields for full-text search with analyzers.
Size shards conservatively: target 10–50 GB per shard. Over-sharding causes coordination overhead; under-sharding limits parallelism.
Separate indices by use case: a search index (optimized for query relevance) should be distinct from an analytics or personalization index.
Interview line: "I would never let Elasticsearch auto-map a new index in production. Explicit mappings are the contract between data engineering and search — changing them later requires a full reindex."

Decision Parameters

  • Is the query exact match or full-text? Use keyword vs text field type.
  • Do we need faceted search (filters by category/brand)? Use keyword + aggregations.
  • Does personalization require vector similarity? Add dense_vector field + kNN query.
  • What is the document update frequency? High churn = consider alias + reindex strategy.
  • Do we need real-time data? Use upsert + refresh_interval tuning.
  • Is this a cold index? Set refresh_interval: -1 and disable replicas during bulk load.

Contextual Glossary

Index

A collection of documents in Elasticsearch. Analogous to a database table. Has a mapping (schema) and is divided into shards.

Mapping

Schema definition for an Elasticsearch index. Defines field names, types (text, keyword, integer, dense_vector), and analyzer settings.

Inverted Index

Core data structure behind full-text search. Maps tokens to the documents that contain them, enabling fast lookups by term.

Shard

A horizontal partition of an index. Enables distribution across nodes. Primary shards are set at index creation and cannot be changed without reindexing.

Analyzer

Pipeline that tokenizes and normalizes text during indexing and querying. Includes a tokenizer (splits text) and filters (lowercase, stemming, stop words).

Alias

A named pointer to one or more indices. Used for zero-downtime reindexing: build the new index, then atomically swap the alias.

Query DSL, Relevance Tuning & Personalization

Build queries that blend relevance, business rules, and user personalization signals.

Search Relevance

Decision Strategy

Use bool query to combine must (required match), should (relevance boost), filter (non-scoring exact match), and must_not clauses.
Use function_score to inject business signals: boost by recency, popularity, editorial weight, or user affinity score.
Use kNN (k-Nearest Neighbors) with dense_vector fields to implement semantic personalization — match content to a user's embedding profile.
Cache filter context aggressively: filters (non-scoring clauses) are cached by Elasticsearch automatically — move non-scoring conditions to filter, not must.
Interview line: "Relevance is a product decision expressed as a query. I use function_score to encode business rules like recency bias or editorial boost, keeping search results aligned with platform goals, not just TF-IDF math."

Decision Parameters

  • Should results change per user? Add personalization signals via function_score or kNN.
  • Are business rules changing often? Externalize boost weights to config, not hardcoded queries.
  • Is query latency too high? Profile with _explain, move conditions to filter context, add replicas for read throughput.
  • Does search need to handle synonyms? Configure a synonym token filter in the analyzer.
  • Is scroll-based pagination needed for large exports? Use search_after for deep pagination instead of from/size (memory-safe).

Contextual Glossary

Bool Query

Compound query combining must (scoring match), filter (non-scoring), should (optional boost), and must_not clauses. The primary building block of Elasticsearch queries.

Function Score

Wraps a query and adds scoring functions (field_value_factor, gauss decay, random) to blend relevance with business signals.

kNN Search

k-Nearest Neighbor search over dense_vector fields. Returns the k most semantically similar documents to a query vector. Used for personalization and semantic search.

Aggregations

Analytics queries that compute metrics (counts, averages, min/max) or buckets (group by category, date histogram). Used for faceted navigation and dashboards.

TF-IDF / BM25

Scoring algorithms that rank documents by term frequency and inverse document frequency. Elasticsearch uses BM25 by default for text relevance.

search_after

Cursor-based deep pagination mechanism. Uses the last document's sort values as a pointer, avoiding the memory cost of from/size at high offsets.

Elasticsearch Operations & Cluster Health

Manage index lifecycle, zero-downtime reindexing, and cluster stability at scale.

Operational Excellence

Decision Strategy

Use aliases for zero-downtime reindexing: create the new index, reindex documents into it, then atomically swap the alias. The application never knows there was a change.
Use ILM (Index Lifecycle Management) for time-series data: automatically move indices from hot (fast SSD) to warm (slower, read-only) to cold (archive) based on age or size.
Monitor cluster health: Green = all primary + replica shards assigned. Yellow = primaries assigned, replicas missing (degraded, not failed). Red = primary shards missing (data loss risk).
Interview line: "Reindexing is the Elasticsearch equivalent of a schema migration. I always use the alias swap pattern so the application sees zero downtime while the new mapping is built in the background."

Decision Parameters

  • Has the mapping changed? Use reindex API + alias swap for zero-downtime migration.
  • Is the cluster yellow? Check unassigned replicas — may need more nodes or reduced replica count.
  • Is indexing throughput too low? Increase refresh_interval, batch bulk requests, disable replicas during load.
  • Are queries slow? Profile with _explain, reduce shard count, add read replicas.
  • Is storage growing unbounded? Implement ILM policy with rollover and delete phases.

Contextual Glossary

Reindex API

Copies documents from a source index to a destination index. Used to apply new mappings, change shard count, or clean up data.

ILM (Index Lifecycle Management)

Automated policy that transitions indices through hot, warm, cold, and delete phases based on age, size, or document count.

Cluster Health

Summary of shard allocation status. Green: all shards assigned. Yellow: replica shards missing. Red: primary shards missing — potential data loss.

Bulk API

Batch indexing endpoint. Significantly more efficient than individual document index requests. Used for initial data loads and high-throughput ingestion.

refresh_interval

How often a new segment is made visible to search. Default 1s. Set to -1 during bulk indexing for maximum throughput, then restore after load.

Rollover

ILM action that creates a new index when the current one exceeds a size or age threshold. Used with aliases to maintain continuous ingestion.

9. CI/CD & Infrastructure as Code

Delivery Excellence

CI/CD Pipeline Design

Build reliable, fast pipelines with staged deployments, automated quality gates, and safe rollbacks.

Delivery Safety

Decision Strategy

Structure pipelines in stages: lint → unit tests → build → integration tests → security scan → deploy to staging → smoke tests → deploy to production.
Use canary deployments for Cloud Run and GKE to route a small traffic percentage to the new version before full rollout — reduces blast radius of bad deploys.
Automate rollback triggers: if error rate or latency crosses a threshold after deploy, pipeline should auto-rollback or alert with one-click revert.
Cache aggressively in pipelines: node_modules, Docker layer cache, and test results. A 10-minute pipeline that runs 50x/day wastes 8+ hours per engineer per week.
Interview line: "A CI/CD pipeline is the automated enforcement of team standards. Every quality decision — linting rules, test coverage thresholds, security scans — should live in the pipeline so it cannot be bypassed under deadline pressure."

Decision Parameters

  • How fast must changes reach production? Optimize for pipeline speed without sacrificing safety gates.
  • Can the team recover from a bad deploy in minutes? Implement one-step rollback.
  • Are secrets managed securely? Use GCP Secret Manager or GitHub Secrets, never env files in repo.
  • Are Docker images immutable and tagged by commit SHA? Enables reproducible deployments.
  • Are integration tests isolated from production data? Use ephemeral test environments.
  • Does the pipeline block on flaky tests? Identify and quarantine them separately.

Contextual Glossary

Cloud Build

GCP-native CI/CD service. Runs build steps defined in cloudbuild.yaml. Integrates natively with Artifact Registry, GKE, and Cloud Run.

GitHub Actions

CI/CD workflows defined in .github/workflows YAML files. Triggers on push, PR, or schedule. Common alternative to Cloud Build for non-GCP-centric teams.

Canary Deployment

Routing a small percentage of production traffic (5–10%) to a new version before full rollout. Reduces risk of widespread regression.

Artifact Registry

GCP service for storing and versioning Docker images, npm packages, and Maven artifacts. Integrates with Cloud Build and Cloud Run.

Rollback

Redeployment of a previous known-good version. In Cloud Run: traffic split revert. In GKE: kubectl rollout undo or Helm rollback.

Quality Gate

A mandatory pass/fail check in a pipeline (test coverage %, lint errors, SAST findings) that blocks deployment if not met.

Infrastructure as Code (Terraform / Pulumi)

Manage GCP infrastructure declaratively for reproducibility, auditability, and team consistency.

IaC Governance

Decision Strategy

Use Terraform for GCP resources: Cloud Run services, GKE clusters, Cloud SQL, VPCs, DNS, IAP, and Secret Manager configurations should all be defined as code, not manually provisioned.
Modularize by concern: separate modules for networking, compute, data, and identity. Each module is versioned and reusable across environments (dev, staging, prod).
Store state remotely: use GCS backend with state locking via Cloud Storage. Never store .tfstate locally or in git — it contains sensitive resource metadata.
Choose Pulumi over Terraform when the team is TypeScript-first and wants type safety, loops, and conditionals without HCL limitations.
Interview line: "Infrastructure as Code is non-negotiable for a consultancy platform. Without it, every new environment is a manual snowflake. With it, spinning up a staging environment is a terraform apply away from being identical to production."

Decision Parameters

  • Is the team familiar with HCL or prefers TypeScript? Terraform vs Pulumi.
  • Are environments consistent? IaC ensures dev = staging = prod, minus config.
  • Can infrastructure changes be reviewed? Use terraform plan in CI for PR reviews.
  • Is state accessible to all team members? Use remote GCS backend, not local files.
  • Are secrets in IaC? They should reference Secret Manager, never be hardcoded.

Contextual Glossary

Terraform

HashiCorp IaC tool using HCL syntax. Defines infrastructure as declarative config. Plan shows changes before apply. Widely used for GCP, AWS, and Azure.

Pulumi

IaC tool using general-purpose languages (TypeScript, Python, Go). Offers type safety and full language features. Good fit for TypeScript-heavy teams.

State File (.tfstate)

Terraform's record of managed resources. Must be stored remotely (GCS, S3) with locking. Contains sensitive data — never commit to git.

Terraform Module

Reusable, versioned Terraform configuration. Encapsulates a logical group of resources (e.g. a Cloud Run service with its IAM bindings and DNS record).

terraform plan

Dry-run command that shows what changes will be made without applying them. Used in CI pipelines for PR review of infrastructure changes.

Remote Backend (GCS)

Stores Terraform state in a GCS bucket with object locking. Enables team collaboration, prevents state conflicts, and survives local machine loss.

Kubernetes Operations on GKE

Manage workloads, autoscaling, access control, and safe rollouts on GKE in production.

K8s Governance

Decision Strategy

Always set resource requests and limits: without them, a single noisy workload can starve the entire node. Requests define scheduling placement; limits cap consumption.
Use HPA for stateless services: scale on CPU or custom metrics (RPS via KEDA, queue depth) rather than manual replica counts.
Separate workloads into namespaces: use namespaces per team or per environment tier to apply RBAC, network policies, and resource quotas independently.
Configure liveness and readiness probes: liveness restarts stuck containers; readiness gates traffic routing — a missing readiness probe causes traffic to reach unready pods.
Interview line: "Kubernetes resource limits are the equivalent of thread-pool sizing in a monolith. Skip them and you get unpredictable cascading failures when one service spikes. Set them and the scheduler becomes a reliable admission controller."

Decision Parameters

  • Is the service stateless? Use HPA + Deployment. Stateful? Use StatefulSet + PVC.
  • Do pods need predictable memory? Set requests = limits for memory to avoid OOM evictions.
  • Are teams sharing a cluster? Enforce RBAC and ResourceQuotas per namespace.
  • Is rollout safe? Use RollingUpdate strategy with maxSurge/maxUnavailable tuning.
  • Does the app need graceful shutdown? Implement SIGTERM handler and preStop hook.

Contextual Glossary

HPA (Horizontal Pod Autoscaler)

K8s controller that scales the number of pod replicas based on CPU, memory, or custom metrics. Requires resource requests to function correctly.

Resource Requests / Limits

Requests: minimum guaranteed CPU/memory for scheduling. Limits: maximum allowed before throttling (CPU) or OOM kill (memory).

Liveness Probe

Checks if a container is alive. On failure, K8s restarts the container. Use for detecting deadlocks or hung processes.

Readiness Probe

Checks if a container is ready to receive traffic. On failure, the pod is removed from service endpoints. Use for startup delays and graceful traffic control.

RBAC (K8s)

Role-Based Access Control for Kubernetes API resources. Defines who (ServiceAccount, user, group) can perform which verbs (get, list, create, delete) on which resources.

RollingUpdate

Default K8s deployment strategy. Replaces pods incrementally. Controlled by maxSurge (extra pods during rollout) and maxUnavailable (pods allowed down).

10. Process, Agile & Stakeholder Leadership

Team Coordination

Sprint Ceremonies & Distributed Team Coordination

Facilitate effective agile processes across timezones and disciplines without ceremony overhead.

Team Effectiveness

Decision Strategy

Sprint planning: separate capacity planning (how many points?) from scope alignment (which stories?). Involve all disciplines — mobile, frontend, backend, DevOps — to surface dependency risks before the sprint starts, not mid-sprint.
Standups with distributed teams: async-first (Slack thread or Loom) for cross-timezone updates, synchronous standup only for the timezone overlap window. Focus on blockers, not status reports.
Retrospectives: use structured formats (Start/Stop/Continue or 4Ls) with anonymous input tools (EasyRetro, Miro) so remote engineers feel safe surfacing issues. Convert every action item to a ticket with an owner.
Definition of Done must include: code reviewed, tests passing, feature flagged if risky, deployed to staging, and documented. Standardize across all disciplines.
Interview line: "A standup is not a status report — it is a blocker-removal meeting. If it runs over 15 minutes, it has become a design session and needs to be scheduled separately."

Decision Parameters

  • Are timezones more than 4h apart? Shift to async-first with recorded updates.
  • Is velocity predictable? If not, check: unclear acceptance criteria, missing DoD, or dependency surprises.
  • Are retros safe? Psychological safety is a precondition — anonymous inputs reduce hierarchy effects.
  • Are stories too large? Split by deliverable value, not technical layer.
  • Does sprint planning take too long? Pre-refine tickets 1 week ahead in a backlog grooming session.
  • Are blockers resolved fast? Tech lead owns blocker removal as primary responsibility.

Contextual Glossary

Velocity

Average story points completed per sprint. Used for capacity planning, not performance evaluation. Fluctuates naturally — meaningful only as a 4–6 sprint trend.

Definition of Done (DoD)

Team agreement on what "complete" means for any story. Typically includes code review, tests, staging deploy, and documentation. Prevents scope creep and rework.

Sprint Review vs Retro

Review = inspect the product increment with stakeholders (what did we build?). Retro = inspect the team process (how did we work?). Do not conflate them.

Backlog Grooming

Session to refine upcoming stories: clarify acceptance criteria, estimate size, resolve dependencies. Prevents planning sessions from being derailed by unclear tickets.

Async-first

Default to written, non-real-time communication for non-urgent coordination across timezones. Preserves focus time and creates a searchable decision log.

Story Splitting

Technique to break large stories into smaller deliverable slices. Prefer splitting by user value (thin vertical slice) over technical layer (backend then frontend).

Client Stakeholder Communication & Risk Reporting

Translate technical risk into business language and maintain trust with US-based clients.

Client Trust

Decision Strategy

Lead with impact, not mechanism: "This architectural risk could delay the launch by 2 weeks and increase infra cost by ~$3K/month" lands better than "we have a N+1 query problem in the ORM layer."
Maintain a living risk register: a simple table of risks, probability (H/M/L), impact (H/M/L), owner, and mitigation status. Share it in the weekly stakeholder update — no surprises.
For scope changes: respond with a trade-off, not a yes or a no. "We can add that feature in Sprint 6 if we defer X, or we can fast-track it by reducing test coverage — which risk is acceptable to the business?"
US timezone alignment: schedule the weekly stakeholder sync at a time that works for US morning (EST/PST) — typically 9–10 AM EST (Mexico City: 8–9 AM CST). Record it for async review.
Interview line: "My job as technical lead is to make sure the client never hears about a risk for the first time on the day it becomes a crisis. I surface risks early, quantify them, and come with options — not just problems."

Decision Parameters

  • Is the risk technical or delivery? Technical risks get mitigation plans; delivery risks get scope trade-off options.
  • Does the client understand the domain? Adjust abstraction level — avoid internal jargon.
  • Is a decision urgent? Escalate async (Slack/email with clear deadline) rather than waiting for the weekly call.
  • Is scope expanding? Document every addition as a change request with effort and trade-off visible.
  • Is trust eroding? Increase transparency — more frequent (but shorter) updates beat less frequent but detailed ones.

Contextual Glossary

Risk Register

A living document listing known risks with probability, impact, owner, and mitigation status. Updated weekly. Shared with stakeholders to prevent surprises.

Scope Creep

Gradual expansion of project requirements without formal change control. Managed by making the cost of additions visible and explicit.

Change Request

Formal record of a scope addition or modification, including estimated effort, impact on timeline, and trade-offs. Creates accountability and shared expectation.

Escalation Path

Defined route for raising blockers or risks that cannot be resolved at the team level. Should be agreed upon at project kickoff, not discovered during crisis.

Status Update Format

Effective format: what we shipped, what is in progress, what is blocked, risks to watch. 3–5 bullets per section. Consistent cadence builds trust more than occasional long reports.

RACI

Responsibility matrix: Responsible, Accountable, Consulted, Informed. Clarifies decision ownership across client, PM, and tech lead to prevent decision paralysis.

Code Reviews & Engineering Standards

Use code review as a quality and knowledge-sharing tool, not a gatekeeping bottleneck.

Quality Culture

Decision Strategy

Automate what machines can enforce: linting (ESLint), formatting (Prettier), type checking (tsc --noEmit), test coverage thresholds. Code review is for logic, architecture, and learning — not style arguments.
Review for intent, not just correctness: "Does this PR solve the right problem?" is more valuable than "Is this the most clever implementation?"
Set PR size norms: PRs over 400 lines are rarely reviewed well. Encourage feature flags to merge smaller, safer increments. Use stacked PRs for large features.
Use code review for mentoring: explain the why behind change requests, not just the what. A question ("have you considered X?") teaches more than a command ("change this to X").
Interview line: "I treat code review as the team's primary knowledge-sharing mechanism. Automate everything a machine can enforce, so human reviewers focus on architecture, intent, and team growth — not semicolons."

Decision Parameters

  • Are reviews blocking delivery? Check PR size, review turnaround SLA, and bus factor on reviewers.
  • Are style debates consuming review time? Add ESLint + Prettier + pre-commit hooks.
  • Are juniors getting useful feedback? Ensure reviews include explanations, not just change requests.
  • Is TypeScript strict mode enabled? Prevents entire categories of runtime bugs at compile time.
  • Are security issues caught? Add SAST tools (Snyk, SonarQube) to the pipeline as a quality gate.
  • Is coverage regressing? Enforce coverage thresholds in CI — fail the build, not the person.

Contextual Glossary

ESLint

JavaScript/TypeScript static analysis tool. Enforces coding rules (no unused vars, no any, import order). Configured via .eslintrc. Runs in CI and as IDE plugin.

TypeScript strict mode

Enables strictNullChecks, noImplicitAny, strictFunctionTypes, and others. Catches most common JS runtime bugs at compile time. Should be enabled from project start.

Stacked PRs

Series of small, dependent pull requests where each builds on the previous. Enables large feature development in reviewable increments without long-lived feature branches.

SAST

Static Application Security Testing. Scans code for known vulnerability patterns (SQL injection, XSS, hardcoded secrets) without executing it. Run in CI pipeline.

Pre-commit Hook

Script triggered before a git commit completes. Used to run lint, format, and type checks locally, preventing fixable issues from reaching CI.

PR Review SLA

Team agreement on maximum review turnaround time (e.g. 24h). Without it, PRs age, create merge conflicts, and block the next ticket.

React Native Deployment & Mobile Workflows

Manage builds, OTA updates, and app store releases for React Native platforms.

Mobile DevOps

Decision Strategy

Use EAS Build for cloud-based native builds — avoids maintaining macOS build machines for iOS. Produces .ipa and .apk/.aab with reproducible environments.
Use OTA (Over-the-Air) updates for JS-only changes to bypass app store review timelines. EAS Update or CodePush can deliver JS bundle updates in minutes vs days.
Limit native module additions: every new native module requires a binary rebuild and new app store submission. Evaluate JS-based alternatives first.
Maintain separate build profiles: development (dev menu, debug), preview (internal testing, no debug), production (store release). Each targets different API environments.
Interview line: "OTA updates are the mobile equivalent of ISR — you push a JS change and users get it without waiting for app store review. I use them for hotfixes and content changes, but never for changes that touch native code or require binary updates."

Decision Parameters

  • Is the change JS-only? Eligible for OTA update without store submission.
  • Does the change touch native code? Requires full EAS Build + store release cycle.
  • Are builds reproducible across team members? Use EAS Build to eliminate local environment drift.
  • Are internal testers getting builds quickly? Use EAS preview profile + TestFlight / Internal Testing track.
  • Is the app using limited native modules? Document them — each one is a build dependency and upgrade risk.

Contextual Glossary

EAS Build

Expo Application Services Build. Cloud-based build service for React Native apps. Produces signed iOS/Android binaries without local Xcode or Android Studio setup.

OTA Update (EAS Update)

Delivers a new JavaScript bundle to users without requiring an app store submission. Limited to JS changes — cannot modify native modules or binary code.

CodePush (AppCenter)

Microsoft OTA update service for React Native. Alternative to EAS Update. Targets a specific deployment key; rolls back automatically on crash spikes.

Build Profile

EAS configuration variant (development, preview, production). Controls signing certificates, environment variables, and distribution target (simulator, internal, store).

TestFlight

Apple's beta distribution platform for iOS apps. Used to distribute pre-release builds to internal testers before App Store submission.

AAB (Android App Bundle)

Android's preferred publishing format. Google Play optimizes delivery per device configuration. Replaces APK for store submissions.
